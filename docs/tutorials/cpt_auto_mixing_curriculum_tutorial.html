一句话结论
系统不是手工填写 278 个数据集在每个阶段的权重，而是只维护数据集基准权重、固定分桶、阶段 bucket 目标占比三层信息，再自动展开为训练框架可消费的 278 维权重 schedule。

核心设计是“桶间重配、桶内保形”。课程只改变 L0–L5 六个桶在训练中的宏观份额；同一桶内数据集的相对权重沿用 v2d15 基线。这样既能控制课程方向，又避免为每个阶段手调 278 个数字。

§1为什么 CPT 数据配比不能靠手工

多模态 CPT 的数据源同时覆盖纯文本、图像问答、文档 OCR、多图、视频、内部业务数据和复杂推理。不同源的样本长度、视觉帧数、质量、难度与领域价值差异很大。只用静态混合会带来三个问题：训练早期被长视频和硬推理扰动；训练后期仍被大量简单开放数据稀释；每次改总 token 数或做消融都要重算大量权重。

§2L0–L5：把 278 维问题压缩成 6 维控制面

分桶来自 v2d15 的类型、数据类型、任务类型与平均 token 等画像列，随后固化为 BUCKET_BY_NAME。固定映射很重要：同一实验矩阵中，课程变体只能改变配比，不能悄悄改变数据定义。

分桶原则
“难度”不是单一标签，而是来源、模态、序列成本、结构复杂度和任务推理强度的联合工程判断。脚本只保存最终分桶，不保存原始画像列，因此版本升级时应在外部保留可审计的分桶生成表。

§3核心算法：桶间重配，桶内相对权重不变

记数据集 i 的基准权重为 bᵢ，所属桶为 g(i)，全体基准权重和为 T，桶 g 的基准权重和为 Bg，某阶段对该桶的目标占比为 qg。自动生成的新权重为：

wᵢ = bᵢ × qg(i) × T / Bg(i)
脚本数值：T = 3652.79786；若 qg = 0，则该桶全部数据集权重置 0。

这个公式同时满足两条不变量。第一，桶内任意两个数据集的新权重比仍等于基准权重比，即 wᵢ / wⱼ = bᵢ / bⱼ。第二，每个桶的新权重和精确等于 qgT，所以六个桶的总权重仍为 T。

def weights_for_targets(targets):
    base_sums = bucket_sums(BASE_WEIGHTS)
    result = []
    for name, base_weight in zip(NAMES, BASE_WEIGHTS):
        bucket = BUCKET_BY_NAME[name]
        target_share = targets[bucket]
        if target_share <= 0:
            result.append(0.0)
        else:
            scale = target_share * TARGET_WEIGHT_SUM / base_sums[bucket]
            result.append(base_weight * scale)
    return result
为什么这比手工权重更稳
新增阶段只需要写 6 个目标占比；替换训练规模只需要改总 token；基准表升级只需要替换基准权重与分桶映射。课程逻辑与数据集细节被解耦，变更面从“278 × 阶段数”缩小到“6 × 阶段数”。

§4curriculum_full：30B token 的五阶段课程

第一阶段使用常量权重；第二阶段开始，每个区间从上一阶段目标线性变化到当前阶段目标。边界以累计 token 而不是 step 定义，因此 global batch、动态 batch 或样本长度变化时，课程仍与实际训练量对齐。

TOTAL_TOKENS 与变体通过环境变量传给内嵌 Python。Python 负责校验和计算，输出 data_config.yaml；Bash 再生成 training_config.yaml 并把前者作为 train_path 接入流式多源数据集。

6.2 Schedule 语义

level: token
boundary_type: token
schedule:
  - init_token: 0
    end_token: 3000000000
    schedule_type: const
    weights: [278 个 S1 权重]
  - init_token: 3000000000
    end_token: 10500000000
    schedule_type: changing
    init_weights: [278 个 S1 权重]
    end_weights: [278 个 S2 权重]

changing 表示区间内从上一目标向下一目标连续变化，而不是边界处突然跳变。脚本设置 level: token，并明确记录 WeightedMultiSourceDataset 会根据运行时平均 token 长度重加权采样；因此应同时观测“配置权重”和“实际消费 token 占比”。

6.3 训练侧配套

案例使用 32K 最大序列、128 帧、global batch 128、micro batch 1、FSDP2 full shard、动态 batch buffer 和 DCP 自动续训。数据调度与模型训练参数分层生成，避免为了改数据课程误改后端或并行配置。

门禁脚本已有检查避免的问题

建议补充的运行时观测
每个阶段记录实际 token、样本数、图像数、帧数和平均序列长度的 bucket/source 分布；比较目标占比与实耗占比；同时按阶段监控 loss、梯度范数、吞吐、OOM/坏样本率和通用/内部评测。只有这样才能判断偏差来自 sampler、长度重加权、数据质量还是课程设计。

§8边界、风险与下一版改进

8.1 当前方案的边界

  • 分桶是离线固定规则：不会根据训练 loss 或能力掌握度自适应调整，因此属于预设课程，不是在线 curriculum。
  • 桶内只保留历史相对权重：若某个源质量显著变化，宏观 bucket 调度无法自动发现。
  • 配置权重不等于实际 token 占比：token-level sampler、动态 batch、长视频与坏样本过滤都可能造成偏差。
  • 阶段目标是经验先验：必须依靠静态基线、无课程终态、提前闭源和降低闭源等消融验证。

8.2 推荐的自动配比 2.0

下一版可以保持现有“六桶控制面”，增加三层反馈：数据画像层按版本自动生成分桶审计报告；采样层根据前一窗口实际 token 偏差做有界校正；实验层用多目标评分选择变体，目标同时考虑通用能力、内部域能力、训练稳定性和单位算力收益。在线校正要设置最大步长与冻结窗口，避免 sampler 与模型学习动态互相放大。

不要直接做无约束 loss-based sampling
高 loss 可能表示“更有学习价值”，也可能表示脏数据、错标或不可学习样本。自动上调前必须结合质量分、重复率、异常率和梯度影响，且设置单源上限。

§9项目与面试表达

60 秒版本
我把 278 个异构 CPT 数据源按来源、模态、序列成本和任务难度固化为 L0–L5 六个桶，只在 bucket 级定义五阶段 token curriculum。系统用归一化缩放公式把六维目标自动展开成 278 维权重，同时保持桶内历史相对配比不变。课程从开放短文本/图像数据预热，逐步引入视频、内部域和复杂推理，内部数据占比从 0% 增至 38%。我还设计了静态基线、无课程终态、提前引入闭源、降低闭源终态四类消融，并用长度一致、占比守恒、分桶完整、实验命名隔离等门禁保证配置可复现。
L1：为什么不直接给 278 个数据集分别设计 schedule？

参数空间过大、难审计且难做公平消融。六桶控制把业务意图映射为少量可解释参数，再由公式保持桶内相对权重，既降低维护成本，也保留历史数据配比知识。

L2：如何证明课程学习有效，而不是最终配比有效？

比较 curriculum_full 与 no_curriculum_final_mix。两者最终目标相同，唯一区别是前者逐步变化、后者从头固定，因此可隔离顺序和渐变带来的增益。

L2：为什么按 token 而不是 step 划阶段？

多模态样本长度和帧数差异大，动态 batch 下每 step 的真实训练量不恒定。token 边界更接近模型实际消费的计算与信息量，也让不同 batch 配置的实验更可比。

L3：如何处理目标占比与实际消费占比不一致？

先按 source/bucket 统计窗口级实际 token，定位长度重加权、过滤和数据可用性造成的偏差；再在不改变课程宏观趋势的前提下做有界反馈校正。任何自动校正都应保留原始目标、修正量和生效窗口，保证可回放。
